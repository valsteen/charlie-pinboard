# Preserve developer navigation

Use this lens when accepted work introduces or changes a command or closed-variant family across several production owners, or places dynamic dispatch on that path. It prevents duplicate routing knowledge before it becomes cleanup work. It is not a repository-wide audit and does not apply merely because a change touches several files.

When an explicitly selected repository-wide storytelling or cleanup pass invokes this lens, repeat it for every distinct routing shape rather than treating one representative trace as complete coverage. The cleanup-specific stress test owns that whole-surface inventory, its eight separate semantic receipts, and its fixed-point rerun; this reference remains the per-shape navigation test.

## Trace the current path

Follow one representative supported value from its external or application entry point through validation, product decisions, conversions, effects or persistence, and presentation. Name every site a developer must discover and classify what it owns:

- boundary validation or an independently required representation conversion;
- product, authorization, or lifecycle decision;
- effect or persistence;
- presentation;
- same-meaning pass-through or remapping.

Names, imports, and direct calls should make the next owner predictable. A site that only converts one already-selected name or same-shaped value into another is a design concern, even when its branch is exhaustive.

At each site, read its names as English claims. Ask whether they truthfully describe where a value came from, when it is current, whether an outcome succeeded or became durable, and what authority or capability the owner actually has. Also notice names that imply intelligence, autonomy, universality, prestige, or identity beyond demonstrated responsibility. Mechanical symmetry cannot rescue a contradictory name. In an explicitly selected storytelling pass, record any mismatch through the storytelling cookbook rather than renaming a stable or deliberate identity from this lens alone.

## Simulate one sibling

Choose one plausible sibling with the same boundary and lifecycle shape. Without implementing it, list the sites that would need edits. Keep an edit site when that owner must validate, decide, convert an independent representation, apply a different effect, persist differently, or present a different result. Fold a site when it only repeats a selection made earlier.

After a concrete alternative has been selected, carry the exact typed value directly until another owner has a different decision or representation to own. Do not add a second route vocabulary, name-to-name conversion table, wrapper variant, or exhaustive branch merely to preserve a layer boundary.

## Choose dispatch deliberately

Keep exhaustive branching where a closed boundary, decision, effect, persistence conversion, or presentation owner genuinely distinguishes the family. Use direct calls or a required protocol when the caller should not distinguish implementations. Use a registry or other dynamic dispatch only for a deliberately open family, with one visible wiring owner, an explicit required surface, and explicit failure for missing support.

Do not hide incomplete handling behind a catch-all branch, mapping default, optional callback, inherited implementation, or default registry handler. Judge the result separately on:

- navigability: the next implementation owner is predictable from the call site;
- refactoring resilience: a new closed alternative forces every required owner to change and cannot fall through;
- boilerplate: no site merely restates an already-selected fact;
- runtime reliability: invalid input, missing wiring, and incomplete implementations fail at a named boundary.

## Preserve the result

For a Pinboard cross-boundary checkpoint, project the representative trace, sibling edit sites, retained exhaustive sites with their owned distinctions, and any dynamic seam's wiring and failure mode into the existing contracts, acceptance criteria, and evidence. Do not create a separate artifact or metric.

Stop when the sibling adds edits only at owners with a distinct responsibility and the route remains predictable without reconstructing a parallel dispatch system.
