# Repository Guidance

- Use Python 3.14.x syntax only. Keep `.python-version`, `requires-python`, Ruff `target-version`, Pyrefly, CI, and the uv lock aligned with the current stable 3.14 patch release.
- Use uv as the only dependency, environment, build, and installed-package entry point. Keep `uv.lock` checked in.
- Do not inject `PYTHONPATH` or another import path, invoke an ambient Python interpreter, add requirements files, or run source files as a substitute for the installed package.
- Match checks to the changed surface. When plugin or skill files change, run `uv run --locked python scripts/validate-metadata.py`; it is the repository-owned platform-compatible metadata check. Run any platform-supplied `quick_validate.py` through the same locked development environment. PyYAML is declared there for validation, so a missing `yaml` module is a broken environment to fix, not an expected limitation to report. Do not provision undeclared one-off dependencies for unrelated optional checks.
- Keep Ruff `UP` as the only pyupgrade authority. Do not add standalone pyupgrade, MyPy, Pyright, or redundant type-checking layers.
- Keep Pyrefly strict. Convert JSON and Markdown boundary values into exact validated types before domain use.
- During review, treat a clean required Pyrefly run as evidence for invariants encoded by concrete types, nominal identifiers, closed unions, and exhaustive matching. Do not require runtime guards, malformed domain objects, or tests solely to cover states that supported typed code cannot express. Continue to require runtime evidence at deserialization, persistence, `Any` or cast boundaries, external inputs, relational state, and concurrency boundaries.
- Declare supported JSON shapes as frozen `msgspec.Struct` records with annotated field constraints and `forbid_unknown_fields=True`, then decode directly into the declared record. Prefer a verbose record declaration over `JsonValue` trees, mapping walkers, field-by-field type checks, or serialize-then-validate round trips. Put cross-field invariants that cannot be expressed declaratively in the record's post-init validation so decoding and instantiation remain one operation. Schema-tagged payloads with no shared shape may use `msgspec.Raw`. Hand-written parsing is acceptable only when the format is predominantly a custom grammar or relational validation makes a declarative codec less clear; document that reason at the owner.
- Keep Python types concrete. Do not use `object` as an annotation escape hatch. When a boundary is genuinely untyped, use `Any`, then validate or narrow it before domain use. Prefer explicit branches over reflective `getattr` or `setattr` loops when the concrete variants are known. Model closed vocabularies without variant-specific data as plain `Enum` values inside the domain. Model closed variants that carry different data as flat dataclass unions rather than a fieldless enum coupled to a separate payload or a polymorphic class hierarchy. Convert strings only at parsing and rendering boundaries. Handle closed branching with exhaustive `match` cases and `typing.assert_never`; write the unreachable arm as `case _ as unreachable:` so the project coverage configuration excludes the statically impossible clause. Do not construct invalid variants merely to execute `assert_never`. Do not use static handler or type dictionaries when the alternatives cannot change at runtime, and do not let a catch-all `else` silently stand for a known variant. Reserve registries and polymorphism for behavior that is genuinely open or runtime-extensible. Never use `StrEnum`.
- Parsing, deserialization, and post-deserialization structural or canonical validation use typed exceptions while values remain boundary representations. Once input has become a domain model, return expected domain and state-machine rejections as explicit values rather than raising exceptions. Use a concrete success value unioned with `DecisionFailure`; use `DecisionFailure | None` when validation has no success value. Propagate the latter with a walrus `None` check when the failure is only returned, and narrow wider unions with exhaustive `match` cases. Infrastructure failures also remain exceptions.
- Keep read-only ledger lookup on `LedgerSnapshot` and return `None` for absence. The decision call site owns the operation-specific failure value; lookup helpers must not combine data access with hidden control flow.
- Model stable opaque string identifiers as distinct `typing.NewType` values. Convert validated external strings once at the owning boundary; do not let storage, Markdown, JSON, CLI, or filesystem representations enter pure decision signatures.
- Name concrete values for their product role or operation, such as `snapshot_items`; do not use architecture-layer prefixes such as `domain_` merely to distinguish them from boundary values.
- Tests must exercise observable behavior, rejection contracts, concurrency, recovery, or package/plugin integration rather than implementation constants.
- Support macOS and Linux. Do not add cross-platform-looking branches without contention and filesystem evidence on the claimed platform.
- Preserve the observable transaction contract: a failed transition leaves the previous valid ledger intact, and concurrent stale actions are rejected.
- Treat Pinboard as a trusted local developer tool, not an adversarial multi-tenant service. Validate human-, agent-, import-, or environment-supplied values once at the boundary that turns them into typed canonical domain values. After an internal producer has established that contract, do not duplicate validation merely to defend against a human deliberately editing authoritative files or SQLite rows, recomputing forged digests, swapping symlinks during an operation, malware changing local state, or another process intentionally violating the repository protocol.
- Keep ordinary path containment at the single boundary that may perform a computed filesystem write, because malformed free-form input or an implementation bug must not accidentally write outside the project root. Do not add repeated path checks, symlink-race defenses, or tamper-proof readback throughout trusted internal layers unless a concrete supported boundary requires them.
- Security-style hardening requires a named threat or failure model and a supported entry path. Reopen stronger defenses when the product accepts untrusted external imports, serves mutually untrusted users, crosses a privilege boundary, shares writable authority remotely, or records an actual corruption incident. A hypothetical hostile local user, forged private ledger, or adversarial filesystem alone is not sufficient scope.
- Treat compatibility code as release-scoped, not permanent architecture. While no external users depend on an older format, use temporary isolated tooling to migrate the known local ledgers, preserve equivalence evidence, then delete the migrator, legacy readers, compatibility branches, and superseded tests before acceptance. Retain current schema detection and clean module boundaries; add a version-specific migration only when a real supported predecessor exists.
- Keep production source, public documentation, and code comments meaningful outside their delivery history. Describe current behavior, ownership, and invariants; keep implementation-plan task or checkpoint numbers, attempt names, milestone labels, and speculative future file paths in private planning artifacts.
- Keep `README.md` human-facing and descriptive. Put imperative agent and contributor constraints here.
- Update `ARCHITECTURE.md` when architectural ownership or dependency direction changes.
